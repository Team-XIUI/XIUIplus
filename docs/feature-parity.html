HeadsUp and native data

Researched October 15, 2026 for the existing-module cleanup. Shared mob information embeds the pinned dataset for Target and its child views; it is not a separate HUD module. The data distinctions below remain authoritative.

HeadsUp reference

The FFXI plugin is Tanyrus/headsup, inspected at commit 80320a89a08290389496d5534bfaa8c3f3339d51.

Its mob information comes from a pinned Phoenix map-server run, rather than client memory or YAML alone. The dump module visits loaded mobs, runs otherwise unspawned mobs through the server's spawn path, and captures script-adjusted attributes. refresh.sh performs the offline server/database work; it is a data-maintenance tool, not something the client plugin runs.

The inspected metadata pins Phoenix commit 9b93232a0cc1e4a5a50b0f988f37d7ae63b8fcfa and records 64,702 mobs across 216 zones from five dumps. That snapshot is not proof of the current live server's state.

MobRecord contains server ID, name, level range, aggression/detection flags, respawn interval, level modifier, placeholder relationships, resistance/immunity references and drops. MobById uses a sorted compiled table and binary search. Native Mob Info now follows that simple model with an embedded pinned snapshot and exact server-ID lookup; its selected fields and availability limits are documented in P06.

Do not copy the previous proposal's name-fallback/provider framework by default. A renamed client mob does not change its server ID, and another server can use different data. Keep unknown records unknown. Preserve HeadsUp/Phoenix GPL notices and asset attributions if reusing their data or code.

Which status data the client actually has

The installed Ashita SDK exposes the following distinct sources:

  • IPlayer::GetStatusIcons and GetStatusTimers supply paired local-player icon IDs and real timer timestamps. GetBuffs supplies the current local icon list. Reuse the existing native clock conversion in experience_source; do not reconstruct duration from spell tables or use PC-clock guesses.
  • IParty::GetStatusIconsServerId, GetStatusIconsTargetIndex, GetStatusIconsBitMask and GetStatusIcons expose the five other members' packed icon IDs. These are actual observed statuses, but the party packet does not include each effect's remaining duration.
  • IResourceManager::GetStatusIconByIndex/GetStatusIconById and buffs.names provide real client artwork, descriptions and names. They describe effects; having a resource record does not prove that an entity currently has the effect.
  • IEntity does not expose a complete arbitrary-mob buff/debuff list or per-effect expiration timestamps in the inspected SDK. Confirmed action/removal messages can establish individual observed mob effects. A base-duration table cannot turn that observation into an exact timer.

The server sources agree. Phoenix 0x063 Status Icons builds the local player's icon/timestamp pairs in 60 Hz units, using 0x7FFFFFFF when an effect has no visible timer. 0x076 Group Effects sends member identity, icon high bits and icon bytes, with no duration list. The inspected local Phoenix tree is commit fbdcc318853b6fda31c03149499049dd6c2eb738; it differs from HeadsUp's dataset pin.

Consequently, real local expiry times and remote estimates must remain distinct. Native access does not reveal server-only remote deadlines. Following the investigation below, Cody requested the original XIUI database as the primary duration catalog for combat observations. The implemented catalog uses fixed literal durations, identifies estimates in hover tooltips, and clears them on observed removal or estimated expiry. Party snapshots still provide IDs without deadlines. Gear/merit/JP/TP formulas and inferred secondary effects remain outside this implementation.

Implemented: original XIUI timer catalog

assets/status/debuff_retail.lua retains the exact imported source from the local tirem/XIUI checkout, with attribution and GPL license. scripts/build-status-rules.py imports fixed spell, weapon-skill, ability, pet, additional-effect and fallback durations into an embedded native header. Runtime lookup uses separate action namespaces and per-effect fixed overrides, then XIUI's known status-duration fallback. No Lua runtime or external data files are needed in the game.

Confirmed gain messages start or refresh estimates; resists, no-effect messages and damage alone do not. Early wear-off/removal/death wins over a later estimate. Estimated expiry removes stale observed icons, including self-buffs whose wear-off was not sent to this player. Missing entries stay untimed. Actual local-player timer pairs retain their exact native deadlines and authoritative local/party lists still decide presence. The historical capture sections below explain why these database timers are estimates.

xiui_module_parity_smoke --status-timers-only checks Paralyze/Blind/Blaze Spikes lookup, action-ID separation, per-effect overrides, estimate labels, native/unknown distinctions, no-effect/resist/damage rejection, confirmed refresh, the captured early Paralyze removal and estimated expiry.

What HeadsUp's mob timers mean

ph_timers handles lottery-placeholder respawns, not buff expiration:

  1. An observed defeat message identifies a known placeholder or an NM associated with placeholders.
  2. Its due time is observation time minus the one-second defeat-message delay, plus the fifteen-second death-to-despawn interval and the dataset's respawn interval.
  3. Seeing the entity alive clears that timer. An overdue entry displays “up” temporarily, then expires.

The local Phoenix mob death path uses a fifteen-second death state and queues its defeat/reward handling after m_DropItemTime, initialized to one second. The respawn schedule and lottery choice remain server state. A countdown derived from those rules is an observed-death estimate, not a native per-mob expiration value; unseen deaths and server changes invalidate assumptions.

Observed-death respawn/placeholder countdowns remain outside this change. Mob Info shows only the optional captured base spawn interval, clearly labeled without a countdown.

Implemented for Party and Alliance HP bars, Player Bar HP, and World Target Bar. Enabled by default on each surface. Visibility and color are separate per surface. Existing settings, text profiles, bar dimensions and row heights are preserved.

Behavior

Native spell-menu selection previews the current party recipient, including native subtarget selection. Once casting starts, the action packet's recipient is locked: moving the hard target does not move the preview. Interrupted, finished, unavailable, dead or out-of-zone targets clear it. A selected spell with insufficient MP or an active known recast does not produce a preview.

This does not change the game's targeting or take input ownership.

The overheal segment extends backward from current HP into the already-filled portion of the bar, leaving the useful green segment visible. Its length is excess healing divided by maximum HP, bounded by the available bar. For example, a 600-HP heal with only 100 HP missing shows 100 HP of useful green healing and 500 HP of pink overheal. At full HP only the pink forecast appears. The default is fully opaque, saturated pink for contrast over the HP fill. A one-time migration updates the former translucent pink default while preserving customized colors and later edits. Both directions use the same meter-range layout, gradients and alpha; MP cost preview clipping is unchanged.

Remote maximum HP is inferred from the party's native current HP and HP percentage when an exact maximum is unavailable. Unknown maximum HP suppresses the segment. Weather/day bonuses, received-healing bonuses, enhanced Rapture equipment, server-specific adjustments and other hidden modifiers can change actual healing. Blue Magic heals, Cura, Waltzes, Regen, items and predictions for other casters are outside this first implementation. No fabricated status durations or combat results are used.

Shared implementation contract

  • Read AGENTS.md, shared foundations, the controller support skill and controller implementation status. Follow the current source when an older proposal differs from implemented behavior.
  • Reuse module registration, config-section/option APIs, native DAT containers, shared meters, text profiles, icon caches and asynchronous settings writers. HUD text uses shared title/meter/caption roles with gradients and normal effects; state colors use TintTextProfile. Compact sizing retains effects. Configuration text has its own presentation.
  • All interactive surfaces provide explicit enter, navigate, activate, details/adjust and cancel routes using the current normalized controller actions/focus graph. Pointer/keyboard/controller invoke the same validated operations. Display-only HUDs need no artificial focus stops.
  • Honor native text/menu/subtarget/gameplay ownership and already-blocked input. Consume owned press/held/release consistently, never repeat destructive/send/activation actions from held Confirm, and release on lifecycle transitions. Keep controller callbacks outside the runtime mutex and use the current host mailbox.
  • Preserve positions, styles, enable flags, drafts and custom settings. New fields use compatibility defaults or narrow versioned migrations; profile round trips include intended preferences. Keep character/device bindings, inventory caches and transient held/focus state out of portable keys. Preserve the immutable XIUI2 preset/dictionary.
  • Distinguish observed values, estimates and unavailable values. Validate client identities and packet bounds; clear stale state on relevant lifecycle changes. Revalidate identity and action eligibility at activation.
  • Cache resources outside rendering and bound transient collections/IO. Bundle approved artwork/data/audio and notices with the existing resource system. The release remains one dist/xiuinative.dll produced by scripts/package.ps1; optional user files must not become mandatory companion dependencies.
  • Changes limited to runtime code can use the current hot-reload workflow when an implementation task calls for it. Host/shared-ABI changes require a coordinated pair in development; a runtime-only publish cannot establish compatibility with an older host.
  • Add only focused checks that exercise meaningful state, ownership, identity, persistence or format boundaries for the implementation. Do not run full suites, repeated builds, asset sweeps or browser/gameplay checks for routine reversible work. Cody checks appearance/gameplay. A proposed validation checklist is not evidence it has run.
  • Record completed scope and source references in the plan and audit. Keep partial work partial until the remaining criteria are met; do not mark future adapters, previews or synthetic-only input as proven native hardware/gameplay support.
